## 1. Mission

Build **the marketplace**, not a portfolio of agents: one place to browse AI agents live on BSC, understand what each one does and how well it performs, and hire it. The winning build gets adopted as BNB Chain's official BNB Agent Studio marketplace.

Judges will personally walk through the product. The single most important thing this build does is let a stranger go from landing page to a completed hire with zero prior context and zero dead ends.

## 2. Judging Rubric → What We're Building

### Main Track (weighted equally, scored independently by 3 judges)

| Criterion | What it means |
|---|---|
| **Functionality** | Land → find an agent by category → understand what it does → activate it, with minimal friction. Someone with zero Agent Studio knowledge must get through it without hitting a dead end. |
| **Data Quality** | Real-time, accurate data beyond basic counts. A user should be able to look at what's shown and make a genuinely informed hiring decision. |
| **Agent Diversity** | All four categories — **rebalancing, grid trading, yield, health factor** — surfaced with **equal depth**. Treating one category as the main event and the rest as an afterthought scores poorly. |

**Eligibility (non-negotiable):** submission must be publicly accessible during judging (real deployment, not localhost). Agents surfaced on the marketplace must be live on BSC — no fabricated listings in the judged build.

### TermiX Challenge (scored independently, on top of main track)

| Criterion | Weight | What "great" looks like |
|---|---|---|
| Value of the services | 30% | Real working agents, priced and fast enough to beat the alternative. TermiX hires from the marketplace themselves. |
| Proven agent advantage | 30% | Measured in the required **Agent Advantage Report**, not asserted. |
| High-stakes categories & track record | 20% | Trading/stock/security agents weighted above general-purpose; trading agents need a real record — win rate, the window it covers, the risk taken. |
| Marketplace quality | 20% | Find, compare, hire — without instructions. |

Everything in this document exists to serve one of the rows above. If a section ever conflicts with this table, the table wins.

## 3. Core Strategy (read this before estimating scope)

Solo, ~2 weeks. Hand-building four fully custom trading bots from scratch is not the efficient path to "Agent Diversity" — **don't do that.**

More than 200,000 agents are already registered on BSC under ERC-8004. The marketplace's job is to **index and surface real ones** across all four categories, not to be the sole source of its own listings. Concretely:

1. **Index third-party agents already on BSC** by reading the ERC-8004 Identity + Reputation registries and classifying by category from each agent's registration file / advertised skills. This is what gives "Agent Diversity" and "Data Quality" real breadth without solo-building dozens of bots.
2. **Build one flagship agent ourselves** — an **ICT/Smart-Money-informed Grid Trading agent** (see §9) — deep enough to carry the TermiX "high-stakes category & track record" criterion and anchor the Agent Advantage Report.
3. **Scaffold three more of our own agents** (rebalancing, yield, health factor) via the BNB Agent Studio CLI, which auto-provisions wallet + ERC-8004 identity + deployment. These need genuinely working (if simpler) logic and real testnet activity — not stubs — but don't need the same bespoke depth as the flagship.

This combination is what makes "equal depth across all four categories" achievable solo in two weeks.

## 5. The Three-Standard Stack (read before writing any chain code)

Three separate, composable standards power this whole category. Don't conflate them.

| Standard | Answers | Role here |
|---|---|---|
| **ERC-8004** | *Who is this agent, and can I trust it?* | Identity (ERC-721), reputation, validation. We read this for every listing. |
| **ERC-8183** | *How do I actually hire it?* | "Job" primitive: Client posts + escrows funds → Provider does the work → Evaluator attests completion or rejection → funds release or refund. States: `Open → Funded → Submitted → Terminal`. |
| **x402 (Binance facilitator)** | *How does the money move?* | HTTP-native payment rail. Server responds `402` with payment terms → client signs an off-chain authorization (EIP-3009 or Permit2) → retries with proof → facilitator verifies + settles on-chain, non-custodially. |

The "Hire" button on an agent page does all three in sequence: look up identity/reputation (8004) → create and fund a job (8183, funded via x402) → poll job state until Terminal.

### 5.1 ERC-8004 — confirmed BSC Testnet addresses

```
IdentityRegistry:   0x8004A818BFB912233c491871b3d84c89A494BD9e
ReputationRegistry: 0x8004B663056A597Dffe9eCcC1965A193B7388713
```
(BSC Mainnet uses different addresses — `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` / `0x8004BAa17C55a88189AE136b182e5fdA19dE9b63` — not needed for this build, testnet is the target.)

**Pull the canonical ABI from `github.com/erc-8004/erc-8004-contracts` (`/abis` folder) — do not hand-type it.** Functions we call, for reference:

- Identity: `register(...)`, `setAgentURI(agentId, uri)`, `getMetadata(agentId, key)`, `setMetadata(agentId, key, value)`, `getAgentWallet(agentId)`, `tokenURI(agentId)`
- Reputation: `getSummary(agentId, clientAddresses, tag1, tag2) → (count, summaryValue, summaryValueDecimals)`, `readAllFeedback(agentId, clientAddresses, tag1, tag2, includeRevoked)`, `giveFeedback(...)`
- Agent identifier format: `{namespace}:{chainId}:{identityRegistry}` + `agentId` → e.g. `eip155:97:0x8004A818BFB912233c491871b3d84c89A494BD9e:agentId`
- `agentURI` resolves to a registration JSON: `{ type, name, description, image, services: [...endpoints], registrations: [{agentRegistry, agentId}], supportedTrust }`. The `services` array is what we parse to classify category and find each agent's callable endpoint.
- We tag our own 4 agents' category on-chain via `setMetadata(agentId, "category", "<REBALANCING|GRID_TRADING|YIELD|HEALTH_FACTOR>")` — cheap, and it's real on-chain data quality, not just a database label.

### 5.2 ERC-8183 — job lifecycle

Roles: **Client** (the hirer — our marketplace user), **Provider** (the agent), **Evaluator** (attests completion; can be an agent, a multisig, or in our simplest version, the marketplace's own attestation service for jobs we control).

States: `Open` (created) → `Funded` (client escrows payment) → `Submitted` (provider delivers) → `Terminal` = `Completed` (evaluator approves, funds release to provider) or `Rejected`/`Expired` (refund to client).

**⚠️ VERIFY before wiring the hire flow:** the deployed job-contract address on BSC Testnet, and whether to call it directly or through BNB Agent Studio's own SDK/API layer. Check:
- `github.com/bnb-chain/bnbagent-sdk` (Python; has an `erc8183` module and a documented `GET /erc8183/status` — suggests Studio may expose a hosted API on top of the raw contract, which would be far less work than reimplementing escrow calls by hand)
- `eips.ethereum.org/EIPS/eip-8183` (the spec itself — still in Draft status, so treat exact function signatures as subject to change and isolate all calls behind one `lib/jobs/erc8183.ts` module so a spec update only touches one file)

### 5.3 x402 — payment flow

```
1. Client requests to fund a job
2. Server responds 402 with payment requirements (amount, asset, recipient)
3. Client wallet signs an off-chain authorization (EIP-3009 transferWithAuthorization, or Permit2)
4. Client retries the request with the signed payload attached
5. Binance's x402 facilitator verifies the signature, submits on-chain, confirms
6. Server receives settlement confirmation, job moves to Funded
```
Supported BSC stablecoins: USDT, USDC, U, USD1. Facilitator is non-custodial — it verifies and settles, never holds funds.

**⚠️ VERIFY before going live:** Binance's specific facilitator endpoint / merchant onboarding steps — check `docs.bnbchain.org` for the current x402 integration guide. Build the payment call behind `lib/payments/x402.ts` with a clean interface (`createPaymentRequest()`, `submitPayment()`, `getSettlementStatus()`) so swapping in the real endpoint is a config change, not a rewrite.

## 6. Data Model (Prisma)

```prisma
enum AgentCategory {
  REBALANCING
  GRID_TRADING
  YIELD
  HEALTH_FACTOR
}

enum JobStatus {
  OPEN
  FUNDED
  SUBMITTED
  COMPLETED
  REJECTED
  EXPIRED
}

model Agent {
  id                String    @id @default(cuid())
  agentIdOnchain    String    // ERC-721 tokenId from Identity Registry
  chainId           Int       @default(97)
  identityRegistry  String
  ownerAddress      String
  agentWallet       String?
  name              String
  description       String
  category          AgentCategory
  imageUrl          String?
  agentUriRaw       String
  services          Json?     // parsed endpoints from the registration file
  isOwnBuild        Boolean   @default(false) // true only for our 4 built agents
  createdAt         DateTime  @default(now())
  updatedAt         DateTime  @updatedAt

  reputationSnapshots ReputationSnapshot[]
  jobs                Job[]
}

model ReputationSnapshot {
  id                   String   @id @default(cuid())
  agentId              String
  agent                Agent    @relation(fields: [agentId], references: [id])
  feedbackCount        Int
  summaryValue         String   // string, not float — avoid precision loss
  summaryValueDecimals Int
  syncedAt             DateTime @default(now())
}

model Job {
  id              String    @id @default(cuid())
  jobIdOnchain    String?
  agentId         String
  agent           Agent     @relation(fields: [agentId], references: [id])
  clientAddress   String
  status          JobStatus @default(OPEN)
  taskDescription String
  budgetAmount    String
  budgetAsset     String    // USDT | USDC | U | USD1
  txHashFund      String?
  txHashSettle    String?
  createdAt       DateTime  @default(now())
  updatedAt       DateTime  @updatedAt
}

model AdvantageReportTask {
  id                String   @id @default(cuid())
  title             String
  category          String   // "trading" | "stock" | "security" | other
  manualTimeMinutes Int
  manualCostUsd     Float
  manualOutputNotes String
  manualOutputUrl   String?
  agentTimeMinutes  Int
  agentCostUsd      Float
  agentOutputNotes  String
  agentOutputUrl    String?
  verdict           String
  createdAt         DateTime @default(now())
}
```

## 7. Backend

### API routes
| Route | Purpose |
|---|---|
| `GET /api/agents` | List + filter by category, sort by reputation/recency |
| `GET /api/agents/[id]` | Detail: description, endpoints, reputation history |
| `GET /api/agents/[id]/reputation` | Live pull-through of `getSummary` if cache is stale |
| `POST /api/hire` | Kicks off ERC-8183 job creation for an agent |
| `POST /api/hire/[jobId]/fund` | Triggers the x402 payment flow, moves job to Funded |
| `GET /api/jobs?client=0x..` | "My jobs" for the dashboard |
| `GET /api/advantage-report` | Serves the TermiX report data |
| `POST /api/cron/sync-registry` | Cron target — see below |

### Registry sync job (every 15 min, Vercel Cron)
Pull `Transfer` events (new registrations) and reputation changes from the two ERC-8004 registries on BSC testnet since last sync, upsert into `Agent` / `ReputationSnapshot`. This is what makes "Data Quality" real — cached for fast page loads, refreshed often enough to count as real-time.

## 9. The Four Agents

| Category | What the hackathon expects | Our approach | Depth |
|---|---|---|---|
| **Grid Trading** (flagship) | Automated strategy within set ranges | ICT/Smart-Money-informed grid: place grid boundaries at liquidity zones / order blocks / fair value gaps instead of naive fixed-% ranges. This is where prior ICT bootcamp knowledge becomes real product differentiation. | Deep, bespoke — this is also the TermiX "trading" flagship |
| **Health Factor** | Track loan positions, act before liquidation | Monitor a Venus Protocol position (BSC's primary lending market), alert/act as health factor approaches threshold | Real, working, simpler strategy |
| **Yield** | Move capital to where it earns most | Compare yields across a small basket of BSC opportunities (Venus supply APY, PancakeSwap LP pools), move on a threshold | Real, working, simpler strategy |
| **Rebalancing** | Maintain a target portfolio allocation | Rebalance a small fixed basket of BSC assets back to target weights on a schedule/threshold | Real, working, simpler strategy |

All four must: be registered via ERC-8004 (real `agentId`, real registration file), execute genuine (even if simple) strategy logic against BSC testnet — not mocked outputs — and get equal presentation quality in the UI (same level of stats, same detail-page layout). Depth of *strategy sophistication* concentrates in Grid Trading; depth of *presentation and data quality* must not.

**Build path:** provision all 4 through the BNB Agent Studio CLI (`npm install -g @bnbagent/studio-cli`, then describe each agent in a prompt) — it auto-generates wallet, ERC-8004 registration, and cloud deployment, which is the fast path to "genuinely live on BSC" for all four. Then hand-deepen the Grid Trading agent's actual decision logic beyond Studio's scaffold.

## 11. Design Direction

Subject: a trading-terminal-grade agent marketplace — the product should *feel* like the "smart money" concept it's selling: signal over noise, information advantage, live order flow. Avoid the generic AI-build defaults (cream background + serif + terracotta; near-black + neon accent; broadsheet columns) — go for a **quiet, dark ledger**, not a crypto-neon dashboard.

**Palette**
- `#0E1116` Ink — base background (blue-black, not pure black)
- `#161B22` Fog — panel/card surface
- `#E9E6DD` Bone — primary text, warm off-white
- `#F5A623` Signal — the one accent; reserved for "live," CTAs, active states
- Muted green/red pair strictly for numeric performance deltas (functional, not decorative)

**Type**
- Display + UI labels: **Space Grotesk**
- All numbers, tickers, addresses, stats: **IBM Plex Mono** (tabular figures — this is what makes it read as a ledger, not a SaaS page)

**Layout & signature element**
Agent listings behave like order-book rows, not SaaS pricing cards: category as a left-aligned eyebrow label, reputation/performance numbers right-aligned in mono. The signature element is a thin, live-updating activity **tape** beneath the hero — real recent on-chain hires and job completions pulled from the sync cache. It's both the visual signature and a running proof of live data.
